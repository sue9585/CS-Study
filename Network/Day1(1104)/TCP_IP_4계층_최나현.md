## 1. 개요 및 정의

웹 요청 하나가 서버에 도착하려면 요청 내용 만들기, 앱 사이의 전달, 목적지 주소 처리, 실제 연결 구간의 전송이 함께 이루어져야 한다.

**TCP/IP 4계층**은 이 통신 과정을 **네 가지 역할**로 나누어 설명하는 모델이다.

- **TCP/IP**: 인터넷 통신에 사용하는 규칙들의 체계. TCP와 IP 외에도 여러 규칙이 포함된다.
- **프로토콜**: 장치들이 데이터를 주고받을 때 지키는 규칙.
- **계층**: 통신에 필요한 역할을 나눈 구분.

### TCP란? — 데이터를 순서대로 전달하는 규칙

**TCP(Transmission Control Protocol, 전송 제어 프로토콜)**는 양 끝의 앱에 **신뢰성 있는, 순서가 보장되는 바이트 스트림을 제공하는 규칙**이다. 네 계층 중 **전송 계층**에 해당한다.

- 일반적인 연결 수립은 **SYN → SYN+ACK → ACK**의 3-way handshake로 이루어진다. 양쪽의 초기 순서 번호를 교환하고 확인한다.
- 데이터에 순서 정보를 붙이고, 받은 쪽의 확인 응답을 활용한다.
- 중간에 빠진 데이터는 다시 보내고, 도착 순서가 바뀌면 순서에 맞춰 앱에 전달한다.

**예시:** `안녕하세요`를 보내는 상황을 생각해 보자. 데이터 일부가 늦거나 빠지더라도 TCP는 앱이 원래 순서의 데이터를 받도록 관리한다. 실제 전송이 글자 단위로 나뉜다는 뜻은 아니다.

> **기억하기: TCP는 “데이터가 제대로, 순서대로 전달되도록 관리하기”.** 연결이 끊겨 복구되지 않으면 전송이 실패할 수도 있다. TCP 자체가 데이터를 암호화하는 것은 아니다.

### IP란? — 목적지 주소를 바탕으로 전달하는 규칙

**IP(Internet Protocol, 인터넷 프로토콜)**는 **IP 주소를 사용해 여러 네트워크를 거쳐 데이터를 목적지로 전달하는 규칙**이다. 네 계층 중 **인터넷 계층**에 해당한다.

- 보내는 데이터에 출발지와 목적지 IP 주소 등을 포함한다.
- 데이터를 운반하는 단위를 **IP 패킷**이라고 한다.
- 중간의 라우터는 목적지 주소와 자신이 가진 경로 정보를 보고 다음 전달 방향을 결정한다.

**예시:** 노트북에서 멀리 있는 웹 서버로 요청을 보낼 때, 목적지 IP 주소를 바탕으로 여러 라우터를 거쳐 전달한다. IP 주소는 전달에 사용하는 주소이고, IP는 그 주소를 이용하는 통신 규칙이다. IP가 경로 전체를 스스로 계산하는 것은 아니다. 각 호스트·라우터는 라우팅 테이블을 조회해 다음 전달 지점(다음 홉)을 선택한다.

> **기억하기: IP는 “주소를 보고 목적지 쪽으로 전달하기”.** IP 자체는 데이터의 도착이나 도착 순서를 보장하지 않는다.

### TCP와 IP를 함께 쓰면?

| 구분 | IP | TCP |
| :--- | :--- | :--- |
| 핵심 역할 | 목적지 주소를 바탕으로 패킷 전달 | 앱 사이에서 순서·손실 등을 관리 |
| 해당 계층 | 인터넷 계층 | 전송 계층 |
| 쉬운 비유 | 주소가 적힌 물건을 목적지로 운반 | 물건이 빠짐없이 왔는지 확인하고 순서대로 정리 |

**TCP 데이터를 IP 패킷에 담아 보내면, IP는 목적지 전달을 담당하고 TCP는 양 끝에서 전달 상태를 관리한다.** 두 규칙은 서로 다른 역할로 함께 작동한다.

이번 발표에서는 **각 계층의 역할, TCP와 IP의 차이, 데이터를 보내고 받는 과정**을 중심으로 알아본다. 연결 방식은 링크 계층을 이해하기 위한 예시로 사용한다.

## 2. 네 계층이란 무엇인가

웹사이트를 여는 상황에 대입하면 이해하기 쉽다.

| 계층 | 맡은 역할 | 웹사이트를 열 때 |
| :--- | :--- | :--- |
| **응용** | HTTP·DNS 등 서비스의 메시지·절차 정의 | 브라우저가 “이 페이지를 보내주세요”라는 요청을 만든다. |
| **전송** | TCP·UDP, 포트로 통신 종단 구분 | TCP가 데이터 순서를 관리하고, 빠진 데이터는 다시 보낸다. |
| **인터넷** | 목적지 주소를 보고 전달하기 | IP 주소를 바탕으로 데이터를 서버 쪽으로 보낸다. |
| **링크** | 바로 연결된 구간에서 전달하기 | 휴대폰과 공유기 사이에서 와이파이로 데이터를 보낸다. |

> **기억할 말: 내용 만들기 → 앱 사이 전달 → 목적지 찾기 → 연결된 구간 건너기**

네 계층이 네 개의 장비를 뜻하는 것은 아니다. 한 기기 안에서도 여러 계층의 처리가 이루어진다.

### 2-1. 우리가 흔히 쓰는 연결 방식은 어디에 해당하는가

와이파이·유선랜·블루투스는 제품명보다는 **연결 기술**이라고 부르면 된다.

| 연결 방식 | 익숙한 모습 | 계층과의 관계 |
| :--- | :--- | :--- |
| **와이파이** | 휴대폰을 공유기에 무선으로 연결 | 링크 계층 |
| **유선랜(Ethernet)** | PC에 랜선을 꽂아 연결 | 링크 계층 |
| **블루투스 테더링** | 휴대폰 인터넷을 노트북에 블루투스로 공유 | 노트북과 휴대폰 사이의 연결을 링크 계층 관점에서 설명 가능 |

**블루투스 이어폰과 테더링은 다르다.**

- 이어폰 연결: 소리를 전달한다.
- 테더링: 다른 기기에 인터넷 연결을 나눠준다.

여기서는 **블루투스로 인터넷을 공유하는 경우**를 다룬다. 모든 블루투스 통신이 TCP/IP를 사용하는 것은 아니다.

### 2-2. 각 연결 방식으로 웹사이트를 여는 과정

#### 먼저, TCP/IP가 처리하는 공통 과정

TCP를 사용하는 HTTPS 통신에서 주소 조회와 연결 준비가 끝났다고 가정한다.

1. **응용:** 브라우저가 HTTP 요청을 만든다. HTTPS에서는 암호화도 적용된다.
2. **전송:** TCP가 포트·순서 정보 등을 사용해 데이터를 전달한다.
3. **인터넷:** IP가 목적지 주소를 포함한 패킷을 전달한다. 라우터는 다음 전달 방향을 정한다.
4. **링크:** 현재 구간의 연결 기술로 데이터를 보낸다. 이 전달은 경로의 각 구간에서 반복된다.
5. **수신:** 서버가 링크 → 인터넷 → 전송 → 응용 순서로 정보를 처리해 요청을 해석한다. 응답에도 같은 계층별 역할이 적용된다.

#### 연결 방식에 따라 달라지는 부분

| 예시 | 첫 연결 구간 | 이후 전달 |
| :--- | :--- | :--- |
| 와이파이 | 휴대폰이 공유기에 무선으로 전달 | 공유기가 외부 네트워크로 전달 |
| 유선랜 | PC가 Ethernet으로 공유기·스위치 등에 전달 | 라우터를 거쳐 외부 네트워크로 전달 |
| 블루투스 테더링 | 노트북이 블루투스로 휴대폰에 전달 | 휴대폰이 LTE·5G를 통해 외부 네트워크로 전달 |

세 경우 모두 TCP 기반 웹 요청을 사용할 수 있다. **첫 연결 기술이 바뀌어도 응용·전송·인터넷 계층의 역할은 유지된다.** 블루투스 사례는 두 기기가 테더링을 지원하고 설정을 마친 경우다.

### 2-3. TCP/IP를 정확히 이해하기 위한 핵심

#### ① 계층별 데이터 단위와 캡슐화

| 계층 | 데이터 단위 | 추가되는 정보의 예 |
| :--- | :--- | :--- |
| 응용 | 메시지·데이터 | HTTP 요청 형식 등 |
| 전송 | TCP 세그먼트 / UDP 데이터그램 | 포트, TCP 순서 번호·확인 응답 번호 |
| 인터넷 | IP 패킷(데이터그램) | 출발지·목적지 IP 주소 |
| 링크 | 프레임 | Ethernet의 경우 MAC 주소와 오류 검출 정보 등 |

상위 계층 데이터를 하위 계층이 자신의 전달 단위 안에 담는 과정이 **캡슐화**다. 수신 측은 링크 → 인터넷 → 전송 → 응용 순서로 정보를 처리한다. 이것이 **역캡슐화**다.

TCP는 데이터를 나누거나 모아 전송할 수 있다. **HTTP 요청 1개 = TCP 세그먼트 1개 = IP 패킷 1개**로 외우면 안 된다.

#### ② TCP는 메시지가 아니라 바이트의 흐름을 전달한다

앱이 `ABC`와 `DEF`를 두 번에 나누어 보내도, 상대 앱은 `ABCDEF`를 한 번에 읽거나 여러 번에 나누어 읽을 수 있다. 순서는 유지되지만, **보낸 횟수와 받는 횟수가 같다는 보장은 없다.**

따라서 메시지가 어디에서 끝나는지는 HTTP처럼 **응용 계층의 규칙**으로 구분해야 한다. 이것이 ‘바이트 스트림’의 의미다.

#### ③ TCP의 신뢰성은 어떤 방식으로 만들어지는가

- **순서 번호(Sequence Number):** 바이트의 위치를 나타낸다. 패킷마다 단순히 1, 2, 3을 붙이는 방식이 아니다.
- **확인 응답(ACK):** 기본적으로 다음에 받을 것으로 기대하는 바이트 번호를 알린다. 시간 초과나 중복 ACK 등의 신호를 이용해 재전송 필요성을 판단한다.
- **순서 복원·중복 처리:** 수신 TCP가 데이터를 순서에 맞게 앱에 전달하고, 중복 데이터가 앱에 반복 전달되지 않도록 한다.

예를 들어 순서 번호 1000부터 100바이트를 정상 수신했다면, 다른 조건이 없을 때 다음 기대 번호는 1100이다. 이는 데이터 바이트를 설명한 예이며 SYN·FIN도 순서 번호 공간을 사용한다.

**ACK는 상대 TCP의 수신 확인이지, 상대 앱이 요청을 처리하거나 DB 저장까지 마쳤다는 확인이 아니다.** 업무 처리 성공은 응용 계층의 응답으로 확인해야 한다. TCP는 암호화도 제공하지 않으며, 복구 불가능한 장애에서는 전송이 실패할 수 있다.

#### ④ 흐름 제어와 혼잡 제어는 보호 대상이 다르다

| 구분 | 해결하려는 문제 | 핵심 기준 |
| :--- | :--- | :--- |
| 흐름 제어 | 받는 쪽의 버퍼가 넘치는 문제 | 수신 측이 알리는 수신 윈도우(rwnd) |
| 혼잡 제어 | 네트워크에 데이터가 과도하게 몰리는 문제 | 송신 측이 관리하는 혼잡 윈도우(cwnd) |

둘 다 전송량에 영향을 주지만, **수신자의 처리 여유와 네트워크의 수용 여유는 다른 문제**다. 송신 중인 데이터의 양은 기본적으로 두 윈도우 중 작은 쪽의 제한을 받는다.

#### ⑤ IP·포트·MAC은 서로 다른 범위를 식별한다

- **IP 주소:** 네트워크 인터페이스에 부여되는 논리 주소. 네트워크 간 전달에 사용한다.
- **포트 번호:** TCP·UDP에서 통신 종단을 구분한다. TCP 연결은 보통 양 끝의 IP·포트 조합으로 식별한다. 같은 서버 포트에 여러 클라이언트가 연결할 수 있다.
- **MAC 주소:** Ethernet·Wi-Fi 같은 링크에서 프레임 전달에 사용하는 주소다. 모든 링크 기술에 같은 형태의 MAC 주소가 있는 것은 아니다.

다른 네트워크의 서버에 보낼 때 첫 링크의 전달 대상은 보통 **서버 자체가 아니라 기본 게이트웨이**다. 라우터를 지날 때 링크 프레임은 새로 만들어진다. NAT·터널링 등이 없는 일반 IP 전달에서는 출발지·목적지 IP는 유지되지만 TTL(IPv4) 또는 Hop Limit(IPv6)은 감소한다.

> **종단 간과 구간별을 구분하기:** TCP는 일반적인 직접 연결에서 양 끝 호스트가 상태를 관리한다. IP는 네트워크들을 거쳐 목적지로 전달하고, 링크 프레임은 각 링크 구간을 건넌다. 중간 라우터가 웹 요청마다 새 TCP 연결을 맺는 것은 아니다.

**범위 참고:** 이번 예시는 TCP 기반 웹 통신이다. TCP/IP 체계에는 UDP도 포함되며, HTTP/3은 QUIC/UDP를 사용한다. 네 계층은 역할을 이해하는 모델이므로 모든 실제 구현이 엄격하게 일대일로 나뉘지는 않는다.

## 3. 실무 / 면접 가능성이 있는 질문

### Q1. 와이파이와 유선랜이 달라도 같은 HTTP·TCP·IP를 사용할 수 있는 이유는?

**A. 연결 구간의 전달과 그 위의 통신 역할이 나뉘어 있기 때문이다.** 와이파이와 유선랜은 링크 계층의 기술이다. 이 연결 위에서 IP는 목적지 전달을, TCP는 앱 사이의 순서 있는 전달을, HTTP는 웹 요청·응답을 담당할 수 있다.

### Q2. TCP 연결은 노트북과 공유기 사이에 맺어지나요, 노트북과 웹 서버 사이에 맺어지나요?

**A. 일반적인 직접 웹 접속에서는 노트북과 웹 서버 사이에 맺어진다.** 공유기는 중간에서 패킷을 전달한다. 가정용 공유기가 주소 변환(NAT)을 하더라도 보통 웹 서버처럼 TCP 연결을 끝내지는 않는다. 다만 프록시 등이 중간에서 연결을 받아 별도 연결을 만드는 구성도 있다.

### Q3. 데이터가 여러 라우터를 지날 때 링크 계층의 전달은 어떻게 반복되나요?

**A. 경로의 각 연결 구간에서 반복된다.** 노트북에서 공유기까지는 와이파이, 다음 구간은 Ethernet을 사용할 수 있다. 라우터는 들어온 링크의 전달 정보를 처리하고, IP 목적지와 라우팅 정보를 확인한 뒤 다음 구간에 맞는 새 프레임으로 보낸다. 프레임은 해당 링크에서 데이터를 운반하는 단위다.

### Q4. IP가 목적지를 찾아준다면 TCP는 추가로 무엇을 담당하나요?

**A. TCP는 양 끝의 앱 사이에서 데이터를 순서대로 전달하고, 손실된 데이터는 다시 보낸다.** IP 자체는 도착이나 순서를 보장하지 않는다. TCP는 포트 번호로 통신 종단도 구분한다. 다만 연결을 복구할 수 없는 상황에서는 TCP 전송도 실패할 수 있다.

### Q5. 서버가 데이터를 받으면 네 계층을 어떤 순서로 처리하나요?

**A. 기본 흐름은 링크 → 인터넷 → 전송 → 응용 순서다.** 링크의 전달 정보를 확인하고 IP 정보를 처리한 다음, TCP가 데이터를 순서에 맞게 모아 응용 쪽에 전달한다. HTTPS에서는 암호화된 데이터를 복호화한 뒤 HTTP 요청을 해석한다. 보내는 쪽에서 덧붙인 정보를 받는 쪽에서 차례로 해석하는 과정을 역캡슐화라고 한다.

### Q6. TCP가 순서를 보장하는데 왜 메시지 길이를 따로 정해야 하나요?

**A. 순서 보장과 메시지 경계 보장은 다르기 때문이다.** TCP는 바이트의 순서를 보장하지만 앱이 몇 번에 나눠 보냈는지는 보존하지 않는다. 응용 프로토콜이 길이 정보나 구분자 같은 방법으로 메시지의 끝을 정의해야 한다.

### Q7. TCP ACK를 받으면 서버의 작업이 성공했다고 봐도 되나요?

**A. 아니다.** ACK는 상대 TCP가 데이터를 받았다는 확인이다. 서버 앱이 처리하기 전에 종료되거나 작업이 실패할 수도 있다. 실제 작업 성공은 HTTP 응답이나 업무 처리 결과 등 응용 계층의 확인이 필요하다.

### Q8. 흐름 제어와 혼잡 제어는 무엇이 다른가요?

**A. 흐름 제어는 수신자 버퍼를, 혼잡 제어는 네트워크를 과부하로부터 보호한다.** 전자는 수신 윈도우, 후자는 혼잡 윈도우를 기준으로 하며 송신 측은 두 제한을 모두 고려한다.
